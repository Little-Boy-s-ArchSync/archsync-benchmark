# D3 module-edge descriptive analysis plan

Version: 0.2.0. Status: proposed before D3 tool execution. This version narrows
`D3-ANALYSIS-PLAN.v0.1.0.md` to the accepted module-only study boundary; it does
not amend the original case packet, create labels, approve a method, or report a
result. Its case population is pinned by the selected `cases.json` SHA-256
`44cc064a3555c90cc20d2a38ab61d67c6af598c1825bf5290cca2269ec801d35`.
The source-bound truth procedure is the candidate
`D3-MODULE-EDGE-TRUTH-RUBRIC.v0.1.0.md`. Neither document is accepted merely
because it exists.

## Question and population

The primary exploratory question is how two tools recover **direct, resolved
cross-group source-module dependencies** on the same pinned TypeScript/JavaScript
case-side source trees. This is not a test of service HTTP, database, cache, or
message relationships, whole-architecture drift classification, an upstream
maintainer-approved policy, or developer productivity.

Retain all 60 captured change cases in the disposition inventory: 56 selected
primary pairs across HyperDX (19), Reactive Resume (17), and Etherpad (20), plus
four context-only cases. The latter are exclusions, never true negatives.
Analyze each selected base and head separately, but retain the case pair as the
sampling unit: 112 possible case-sides do not become 112 independent changes.
Overlapping revisions, paths, and module edges must be flagged; repeated sides
do not enlarge the independent sample. Report each repository separately before
any pooled descriptive count.

## Freeze before predictions

The accepted method record must bind exact hashes for scope, occurrence/edge
truth rubric, historical rule-applicability ledger, module-group mapping,
analysis plan, source/object manifests, both tool packages and configurations,
resolver policy, source filter, matching implementation, and execution commands.
The common capability must be established on non-D3 development fixtures first.
Only ES value imports/re-exports and supported literal `require`/dynamic imports
may enter the shared comparison. Type-only references, tests, generated/vendor
files, computed specifiers, unresolved targets, package-export differences,
ambiguous symlinks, and out-of-scope groups need explicit frozen treatment; no
tool may silently receive a broader or easier task. Preserve excluded and
unsupported observations with reasons. Do not run either tool on the D3 cases
until both authors accept the same byte-pinned method and the original truth
reviews are sealed.

## Truth and matching units

Each author first inventories all eligible production changed files at base and
head, including files with zero in-scope imports. A proposed occurrence records
case, side, full commit, source file, line/column, literal source quote, syntax
kind, specifier, resolved target, mapping, byte hash, and source/config evidence.
`unresolved`, `unsupported`, `out-of-scope`, and `Unknown` remain distinct.
Neither ArchSync nor dependency-cruiser output is a truth source. AI may help
read source, but each review retains its prompt/output reference, sharing status,
and actual author verification extent. Preserve the two original reviews and
hashes before comparison; report their original differences, then reconcile
jointly. Unresolved disagreements remain `Unknown`. Both reviewers are
development-associated, prediction-exposed, and nonblind; agreement cannot be
called independent ground truth.

The primary scored unit is a deduplicated direct cross-group edge keyed by
`(repository, case, side, source group, dependency type, target group)` under the
frozen group map. Keep source/target file endpoints and syntax occurrences as
diagnostic inventories so group aggregation cannot hide localization errors.
The same edge on base and head is retained on both sides for recovery scoring;
it is **not** an introduced edge. A case label or a single quoted import is not
an exhaustive edge census. If the two tools cannot emit a comparable edge for
a declared feature, record the capability gap and do not force an unfair score.

## Denominators and descriptive measures

For every repository and tool, report captured, selected, eligible, attempted,
completed, unsupported, failed, truth-Unknown, and scored case counts. At the
edge level report source-reviewed truth edges, unresolved truth units, predicted
edges, true positives (exact frozen key match), false positives, and false
negatives on the **same supported subset**. Report `TP/(TP+FP)` as precision and
`TP/(TP+FN)` as recall only for positive denominators. Report F1 as
`2TP/(2TP+FP+FN)` only when precision and recall are both estimable and the F1
denominator is positive. Use `not estimable`, never `100%`, for a zero denominator.
Report both conditional scores on supported/scored inputs and all-attempted
coverage, keeping crashes and unsupported resolution visible. Do not silently
discard a failed case from a paired comparison or count an `Unknown` as correct.

The analysis may show per-repository paired differences on the frozen common
subset, including where either tool has an advantage, equal result, or failure.
No significance test, causal speed claim, general-population superiority, or
independent-holdout accuracy is justified by these purposively selected,
overlapping cases and development-associated truth reviews. Runtime, if
reported, needs pinned hardware, OS, workload, cache state, repetitions, and
raw timing; deterministic reruns are repeatability observations, not new cases.

## Secondary rule findings and stopping rule

The four conditionally accepted module restrictions are secondary descriptive
checks only after the 152 historical rule/case-side applicability decisions and
relevant base/head edges are source-verified. Report historically applicable
sides, newly introduced violations, pre-existing violations, no-new-violation
sides, Unknown, and unsupported separately. Etherpad's selected cases do not
change the exact `DB.ts` source module, so an all-negative rule sample cannot
demonstrate positive-class detection. If introduced positives are zero, their
recall is not estimable. Do not infer `evolution` or whole-architecture
`no-impact` from this module-only inventory.

Run the frozen population with the predeclared tool versions and repetition
count. Retain every command, UTC time, source/config/package hash, raw
stdout/stderr, exit code, edge artifact, failure, and Unknown. A fix made after
seeing D3 output is a post-hoc amendment: preserve the original failed run and
do not relabel the rerun as an untouched holdout. Only source-verifiable,
recomputable measured results may enter the paper, with the author involvement,
AI assistance, prior prediction exposure, and exploratory scope disclosed.
